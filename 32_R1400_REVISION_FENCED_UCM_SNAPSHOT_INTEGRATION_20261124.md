## Critical remaining one-owner integration barriers discovered (stop unsafe cutover)
1. `Engine::receive_batch_inner` calls UCM on **accepted AND rejected** messages, transport-only keepalive and old-generation lifecycle; `Engine::tick_inner` every 50ms mutates UCM and calls 80 per-scope selections. Cannot safely replace 30+ direct `self.manager` usages by merely spawning an actor. Need an ordered event encoder that covers Connect/Subscribe/Close/Reconnect/Quarantine/Observe/TransportOnly/Tick, and **all** UCM read/write operations including readiness-mask history, dual-HOT history, quality hysteresis/active commit/retire. R1399 worker currently does not expose an ACK for `CommitActive` nor implement readiness-mask/dual-HOT transition events (R1385) — must be added before real cutover.
2. **Global revision is conservative but may starve**: existing `poll_proposal`/`poll_snapshot` currently rejects a view whenever ANY source changes after it was requested. At 868–1218 frames/s across 40 bases/2 venues, an unrelated ETH update can invalidate a prepared BTC snapshot. This is safe but can block all HOT availability. Design scope-local source revision fences while preserving **global ordered event delivery** and connection-group invalidation before runtime enablement. Do not relax revision checks without proof.
3. A snapshot read only works with the original selected `SourceId` identity and the latest Engine validated book witness/epoch. Final `Engine` must re-check current 800/801ms expiry (two clocks), source generation, TWO distinct independently HOT connections, book checksum/sequence/witness, highwater, selection/authority atomic commit. A stale or late response may never grant a Permit. `CommitActive` currently queues without guaranteed ACK; must implement bounded reliable completion or async response before publishing and avoid blocking the main queue.
4. Snapshot copies UCM `SourceHealth` maps and calculates quality percentiles on worker. With only 3 vCPUs, extra CPU/cloning could worsen tail latency, so need controlled offline same-input timing and CPU before actual public-quote experiment. The R1399 full mailbox fail-closed is safe but under burst might reduce liveness; no automatic fallback to second mutable UCM.
5. There are existing R1352 lossy diagnostic workers, NOT appropriate for authoritative events; a new Tokio queue/clone or 2nd live UCM would violate one-owner goal. Keep one existing R1399 bounded mailbox and one original Engine/reader runtime; no new project/branch/target.
